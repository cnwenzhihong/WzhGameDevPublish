Gameplay

基本函数

Question

UE 里 Tick 默认每帧都会执行。

👉 什么情况下你绝对不应该用 Tick？你会用什么替代？

当逻辑不需要每帧执行时，不应该用 Tick。
比如：

  • 事件驱动逻辑（输入、状态变化）
  • 定时行为（用 Timer）
  • 一次性流程（用 Ability / Task / Delegate）

Tick 会带来性能开销和逻辑复杂度，
如果可以用事件或回调驱动，就应该避免使用 Tick。

基本变量

Question

TWeakObjectPtr 和 TObjectPtr 区别？

👉 各自适用场景？

区别是：

  • TObjectPtr：强引用，会被 GC 追踪（替代裸指针 UPROPERTY）。
  • TWeakObjectPtr：弱引用，不会阻止对象被 GC 回收

使用场景：

  • TObjectPtr：正常成员变量
  • TWeakObjectPtr：避免循环引用、缓存对象、临时引用

优化

Question

你会如何判断哪些逻辑必须每帧执行，哪些可以优化或异步处理？请具体说明你的判断依据和优化方法。

我会先通过 Unreal Insights 分析当前 Tick 的性能开销，确定最消耗帧时间的逻辑。接着，我会将那些与渲染、物理或动画驱动紧密相关的逻辑保留在 Tick 内，比如角色位置更新和摄像机跟随。而对于复杂计算、大型查询或资源加载，我会使用异步任务或事件驱动来执行，确保它们不阻塞主线程。最后，我会引入自定义的调度系统，根据逻辑重要性和帧率需求，动态调整 Tick 的频率，这样在高端和低端设备上都能保持平衡的表现。”

这种回答不仅有步骤，还体现出你的实际操作方法和对系统整体的理解。

客户端收到服务器同步的数据并修改后调用.

他和RPC的区别是什么:
RPC是主动调用的函数,OnRep是被动的回调.

在客户端生成武器时,owner没有同步过来,导致渲染判断失误.这本质是一个网络时序问题。

RPC和Replicate

RPC和属性复制的区别

Replication（网络复制）只能单向，部分从服务器复制到客户端
RPC远程过程调用：方向是任意的，类似函数调用，不能有返回值
RPC是不可靠的，带宽饱和时可能被丢弃，但它的发送速度和频率高于 可靠RPC(标记reliable)，用于不重要但更新频繁的数据
标记reliable之后变可靠，但一次发送的可靠rpc不能太多，否则会导致网络断开

属性回调OnRep_与RPC的差异？

属性回调理论上一定会执行，而RPC函数有可能由于错过执行时机而不再会执行。

Example

服务器上面有一个宝箱，第一个玩家过去后，宝箱会自动开启。如果使用RPC函数，当第一个玩家过去后，箱子执行多播RPC函数触发开箱子操作。但是由于其他的玩家离这个箱子很远，所有这个箱子没有同步给其他玩家，其他玩家收不到这个RPC消息。当这些玩家之后再过去之后，会发现箱子还是关闭的。
如果采用属性回调，但第一个玩家过去后，设置箱子的属性bOpen为true，然后同步到所有客户端，通过属性回调执行开箱子操作。这时候其他玩家靠近箱子时，箱子会同步到靠近的玩家，然后玩家在客户端上会收到属性bOpen，同时执行属性回调，这时候可以实现所有靠近的玩家都会发现箱子已经被别人开过了。

RPC与Actor同步谁先执行？

不确定。
一般来说，RPC的数据会立刻塞到SendBuffer里面，而Actor的同步要等到NetDriver统一处理。
不过由于存在丢包延迟等情况，这个结果在网络环境下不能确定。

那么这个问题会造成什么后果呢？

  1. 当你创建一个新的Actor的同时（比如在一个函数内），你将这个Actor作为RPC的参数传到客户端去执行，这时候你会发现客户端的RPC函数的参数为NULL。
  2. 你设置了一个bool类型属性A并用UProperty标记了一个回调函数OnRep_Use。你先在服务器里面修改了A为true，同时你调用了一个RPC函数让客户端把A置为true。结果就导致你的OnRep_Use函数没有执行。但实际上，这会导致你的OnRep_Use函数里面还有其他的操作没有执行。

Replicate问题

Replicated 不生效怎么查

Question

一个变量标记了 Replicated，但客户端就是不同步。

👉 你排查的前三步是什么？

⚠⚠⚠质疑、质疑，还是质疑

第一，检查代码
确认变量标记为 Replicated，并且在 GetLifetimeReplicatedProps 注册。
第二，检查Replicate触发前提
Actor：确认 Actor 本身是 Replicated，并且是由服务器生成并同步下来的。
变量修改：确认修改发生在服务器，而不是客户端。
第三，检查网络相关性
确认网络相关性（NetCullDistance / Owner / Relevancy）。
第四，用日志或断点确认服务器是否真的改了值。

Actor被同步到客户端后什么时候能使用其同步属性(尤其是Role_Autonomous)

普通属性+ Gameplay框架的Obj指针：
construct和PostInitializeComponents中不可用
Actor最早可用是PreBeginplay，最稳的是PostBeginpaly/OnRep_
刚开始RPC到客户端的Actor初始属性(尤其是Owner)没有同步过来，会造成引擎自身逻辑都存在bug，比如FPS渲染判定过早，导致的不会隐藏全身模型。

非Gameplay框架的Obj指针：
不确定：需要通过FNetworkGUID等待那个Obj也从服务器同步过来，但慢于Beginplay依旧是极少情况。此时也才会触发OnRep_
Gameplay框架的Actor一般早就同步过来了，自然不需要担心。

哪些UObject对象的引用可以在网络上传递成功
  1. 标记replicate
  2. 从数据包直接Load
  3. 通过Construction scripts添加或者C++构造函数里面添加
  4. 使用UActorComponent::SetNetAddressable标记（这个只针对组件，其实蓝图里面创建的组件默认就会执行这个操作）
OnRep执行问题

同步操作触发是由服务器决定的，所以不管客户端是什么值，服务器觉得该同步就会把数据同步到客户端。
而回调操作是客户端执行，所以客户端会判断与当前的值是否相同来决定是否产生回调。

##### GetLifetimeReplicatedProps

常见条件：
仅同步给所属客户端：DOREPLIFETIME_CONDITION( AActor, ReplicatedMovement, COND_AutonomousOnly );
仅在初始化时同步一次：COND_InitialOnly
哪怕值一样也执行OnRep_：DOREPLIFETIME_CONDITION_NOTIFY( AActor, XXX, COND_Custom, REPNOTIFY_Always );

应用

服务器客户端不一致问题

Question

玩家开火时，有时候客户端已经播放了开火动画和特效，但服务器没有判定命中👉 你会怎么排查和定位这个问题？

  • 网络层（RPC / 延迟 / 丢包）
  • 逻辑层（服务器判定）
  • 表现层（客户端预测）
  • Debug 方法（非常关键）
    我会分三层排查这个问题：

第一层是客户端表现层。
客户端已经播放了开火动画和特效，说明 Ability 已经成功触发，
本地预测逻辑是正常的。

第二层是网络层。
我会检查是否存在延迟或丢包，比如客户端开火 RPC 是否成功发送到服务器，
服务器是否及时返回命中结果。
可以通过日志或网络模拟（Net PktLag / PktLoss）来验证。

第三层是服务器逻辑层（最关键）。
服务器才是命中判定的权威，
我会重点检查服务器在开火那一帧使用的参数，比如：

  • 开火时的角色位置
  • 朝向（Aim）
  • Trace 起点和方向
  • 目标位置

然后和客户端做对比，确认是否存在状态不一致。

常见问题是：
客户端和服务器的位置或朝向有偏差，
导致客户端看起来命中，但服务器 Trace 没打中。

最后是 Debug 手段：
我会在客户端和服务器分别打印开火时的 Transform 和 Trace 数据，
或者用 DrawDebugLine 在两端画出射线，对比是否一致。

总结来说，这类问题通常是：
客户端预测和服务器权威计算不一致导致的表现偏差，
需要通过日志和可视化手段定位具体差异。

框架

GAS的优点，为什么是GAS

方便快速实现和迭代Gameplay多人游戏机制(官网)。个人理解：工程量越大，越方便
等级、费用、冷却、属性、网络复制、GE、完整的客户端预测，极大方便了开发和代码复用，GA的即插即用也几乎不会影响其他代码
GameplayTag几乎取代了关键bool、enum、int值
Cue统一了视觉和音效反馈

对rootmotion蒙太奇的网络支持。

GameplayTag的优点

优点：

  1. 架构：带层级关系。提供复杂查询支持，且查询函数参数化。
  2. 使用：系统只关心Tag，而不需要专门Cast然后获取变量，自带回调和Task。
  3. 网络：同步很快，因为CS两边有相同的GameplayTag表，(需要开启Fast Replication)
    结果：几乎取代了Gameplay的bool、enum，TagCount取代了int值

GAS的缺点

GameplayEffect 延迟调节(Latency Reconciliation).（无法预测技能CD，高延迟玩家相比低延迟玩家, 对于短CD的能力存在更低的激活速率）。
不能预测性地移除GameplayEffect. 然而我们可以反向预测性地添加GameplayEffect, 从而高效的移除它. 但是这不总是合适或者可行的, 因此这仍然是个问题.

Ability

触发

Question

CanActivateAbility 和 CommitAbility 的区别？

👉 为什么两个都需要，而不是只用一个？

CanActivate 是“是否允许进入 Ability”
Commit 是“在执行关键逻辑前再次确认并统一Commit资源”

比如GA起手动作，只需要在地面就可以触发，但在实际打出前并不会消耗法力，用户也可以随时取消。但Commit后，不仅仅是最终检查，则该技能已经生效，Cost触发，冷却触发。

GamePlayTag

Question

Lyra 使用 GameplayTag 而不是 bool

本质是为了数据驱动和系统解耦。

  1. Tag 具有层次结构。
    bool 只能表示单一状态，比如 bIsSprinting，
    但 Tag 可以组合，比如 Ability.State.Jump可以直接记录Ability.State.Sprinting.Start、Falling、Land

2，TagCount 可以表达叠加关系
比如多个系统同时施加同一个状态，只有计数归零才真正移除。还可以完全当作int使用。

  1. 数据驱动
    策划可以在配置中直接增删Tag，不需要改代码和编译
    非常适合 Lyra 这种模块化框架。
  1. 解耦
    比如移动系统只关心是否有 Sprint Tag，不需要Cast到特定的类型。不同Actor类也可以用同一个Tag
  1. 支持 GameplayTagQuery
    复杂条件判断，这在复杂技能关系中非常重要。
  1. GAS 本身就是围绕 Tag 构建的，
    Ability 的激活、阻挡、状态同步、效果应用，都是通过 Tag 控制的，
    所以使用 Tag 可以和整个系统天然对齐。

TagRelation

TagRelation相比较Ability内处理关系的优点：
只需要关心Tag，不需要考虑是GA还是GE触发的，同时，GA也可能是在中途才会添加某些Tag。

Lyra中TagRelation的需求变复杂：

  • 冲刺不能开火
  • 瞄准可以开火
  • 换弹时不能冲刺
  • 某些武器允许“冲刺射击”
    你会怎么设计这个 Tag 系统，避免逻辑越来越乱？

一、将 if 判断改为 GameplayTagQuery
比如开火 Ability：

  • Blocked Query：有 State.Reloading 时禁止
  • Blocked Query：有 State.Sprinting 且没有 Weapon.AllowSprintFire 时禁止
  • Required Query：武器处于可开火状态

二、单层架构改为Layer层级：普通武器使用默认规则，特殊武器动态添加Tag关系
这样系统分三层：

  1. 角色基础状态规则
  2. 武器默认规则
  3. 特殊武器覆盖规则

Attribute

Question

为什么要存在BaseAttribute和Attribute两个数值

可以区分立即生效的GE以及计时/无限生效的GE引发的数值变化
比如Damage，装备手枪时可以设置Damage的Base为10，那么给角色上Buff，只需要改成Damage的临时值+4=14，如果此时换成步枪，Damage的Base直接被设置为20，临时值则会动态变化为20+4=24。Buff时间结束后去掉临时值+上的4即可

Question

为什么要存在Damage这样的metaAttribute

不只是伤害。只要某个数值是“本次事件的输入/中间量”，而不是长期状态，都适合做 MetaAttribute。
如复杂Mana Cost，更复杂的Damage-ShieldDamage-HealthDamage，经验XP，金币收益，状态累计值(PoiseDamage、StaggerDamage)、破防 / 硬直 / 架势条

Attack applies FreezeBuildUp = 30
  ↓
AttributeSet 累加 FreezeMeter
  ↓
FreezeMeter >= Threshold
  ↓
Apply Frozen GameplayTag / GameplayEffect

Question

为什么要使用BaseDamage这样的metaAttribute来处理伤害

把“伤害的计算”和“生命值被修改”解耦。
技能、武器、GE、ExecCalc 只负责算出“这次造成多少伤害”；真正扣 Health、触发死亡、广播事件、处理护盾/抗性/免伤，则集中放在 AttributeSet::PostGameplayEffectExecute() 或伤害执行逻辑里处理。

除了Damage，Lyra中还有治疗量Heal也是一样的属性(ULyraCombatSet)

GC原理

UE采用标记-清除的垃圾回收方式，是一种经典的垃圾回收方式。一次垃圾回收分为两个阶段。第一阶段从根集合开始，遍历所有可达对象，遍历完成后就能标记出可达对象和不可达对象了，这个阶段会在一帧完成。第二阶段会渐进式的清理这些不可达对象，因为不可达对象永远不能被访问，所以可用分帧清理，避免卡顿
虚幻的根集合就是创建Object的时候，调用AddToRoot方法中加入的集合

GC算法类型

  1. 标记清除–先标记可达或不可达，然后把不可达清除
  2. 复制算法–两块相同的内存，每次使用一块，用完了，整体把还存活的对象复制到另一块，然后清除整块内存
  3. 标记整理–标记过程和标记清理算法一致，但标记后会把可达对象全部移动到内存另一端，完成后把另一端清除
  4. 分代收集–按存活时间把对象分成几个区域，然后不同区域按照其他三种算法择优进行回收，更新更快的区域使用复制算法，更新慢的使用标记算法

UPROPERTY

简述UPROPERTY()的作用

Important

没有 UPROPERTY，UE 就不知道这个变量的存在

UPROPERTY 把一个普通 C++ 变量，接入 UE 整个对象系统（GC、反射、网络、编辑器）的关键入口。

第一是垃圾回收（GC）。
UE 的 UObject 是通过 GC 管理的，
只有被 UPROPERTY 标记的指针，才会被 GC 系统追踪引用关系。

第二是反射系统。
UPROPERTY 会把变量注册到 UClass 的反射信息里，
可以用于序列化、编辑器、蓝图访问、网络同步等。

第三是网络同步。
通过 Replicated、OnRep 等标记，可以让变量参与网络复制。

第四是序列化和存档。
比如 SaveGame、Config，可以控制变量是否参与存档或配置文件。

第五是编辑器和蓝图支持。
比如 Category、EditAnywhere、ClampMin，可以控制在编辑器中的表现。

问题

Question

UE 里为什么不推荐直接用 new/delete 来创建 UObject？

应该用什么？为什么？

第一，UObject 的生命周期由 UE 的 GC 管理。
如果用 new 创建，UE 的 GC 系统不会追踪这个对象，
即使还有引用，也可能被错误回收，或者永远不会被释放，导致内存问题。

第二，UObject 必须挂在一个 Outer 上，形成对象层级。
NewObject 会指定 Outer，让对象进入 UE 的对象体系，
比如 World、Actor 或 Component，这样 UE 才能正确管理它的生命周期。

第三，反射和序列化系统依赖 UObject 体系。
用 NewObject 创建的对象会注册到反射系统，支持蓝图、序列化、网络同步等功能，
而 new 出来的对象完全脱离这些系统。

第四，Actor 有更特殊的生命周期。
必须通过 SpawnActor 创建，才能正确注册到 World，
参与 Tick、网络同步、碰撞、渲染等系统。

总结来说：
new 创建的是“纯 C++ 对象”，而 NewObject / SpawnActor 创建的是“UE 管理对象”，
两者属于完全不同的生命周期体系。

动画系统

Question

为什么很多 FPS 项目会用 单独的 ViewModel Mesh（手臂），而不是直接用角色全身 Mesh？

本质是最佳体验问题，FPS最好的的体验一定会牺牲TPS动画的表现，不可能兼顾。很多在FPS视野内正常的动画，实际上全身Mesh已经扭曲得不成样子。

ViewModel Mesh一方面可以方便动画师专注于摄像机视野内的效果，而不需要考虑视野外是怎么扭曲变形的。

从程序上考虑，ViewModel很多逻辑也和全身Mesh不一致，很多动画只需要在ViewModel执行，比如检视动画，TPS完全没必要播放，播放后也会很奇怪。
不同渲染方式也可以使用不同 FOV 和渲染参数，避免穿模和比例问题。以达到最佳体验。

总之，这本来就是两套完全不同的体验，不能因为看起来像就强行融合。
